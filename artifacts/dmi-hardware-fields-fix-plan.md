# Plan: fix `serial_number` (root cause: unprivileged read denial), add `uuid`/`manufacturer`/`product_name`

## Background (already established — do not re-litigate)

- `crates/pharos-pulse/src/main.rs`'s `get_serial_number()` (Linux path,
  line ~291) reads `/sys/class/dmi/id/product_serial` and falls back to
  `"unknown"` on any read failure — this fallback has silently masked total
  failure in production the whole time, since `unknown` values are then
  filtered out of the inventory payload entirely
  (`inv.retain(|_, v| v != "unknown")`), so the field never even reaches
  the server.
- **Not a Podman-testable bug in isolation**: this is a real filesystem
  permission problem on the *host's* sysfs, not something a container's
  isolated environment reproduces faithfully (containers typically don't
  expose an independent, permission-settable DMI subsystem — it's either
  absent or read-only bind-mounted from the host). Live verification of
  the actual fix requires a real bare-metal or VM host, not just Podman —
  say so explicitly when reporting results, don't overclaim Podman-only
  verification as sufficient here.
- macOS's `get_serial_number()` (via `ioreg -rd1 -c IOPlatformExpertDevice`)
  and Windows's (via `Get-CimInstance Win32_Bios`) do **not** have this
  permission restriction — this fix is Linux-only. Confirm this assumption
  is actually still true empirically if a macOS/Windows host is available,
  rather than just trusting it, but do not block the Linux fix on that.
- Sysfs entries are regenerated by the kernel at every boot — any
  permission grant must be **re-applied at every boot**, not just once at
  install time. A one-time `setfacl` in `install.sh` would be silently
  lost on the next reboot.
- Panel-selected mechanism: a `systemd-tmpfiles.d` drop-in using ACL
  (`a`-type) entries, applied automatically at every boot via the
  already-existing `systemd-tmpfiles-setup.service` (runs early, before
  `pharos-pulse.service`, with no new explicit unit ordering needed) —
  narrower than a systemd capability grant (`AmbientCapabilities=`) or a
  scoped `sudo`/setuid path to `dmidecode` (both considered and rejected
  as broader than necessary for a two-file read grant).

## The change

### 1. `scripts/install.sh`'s `install_pulse()`: grant narrow, boot-persistent read ACLs (Linux only)

Install a tmpfiles.d drop-in, e.g. `/etc/tmpfiles.d/pharos-pulse-dmi.conf`:
```
a /sys/class/dmi/id/product_serial - - - - u:pharos:r
a /sys/class/dmi/id/product_uuid   - - - - u:pharos:r
```
Apply it immediately during install too (`systemd-tmpfiles --create /etc/tmpfiles.d/pharos-pulse-dmi.conf`), not just wait for the next boot, so the fix takes effect without requiring an immediate reboot. Gate this whole step on Linux (`install_pulse` already knows the target OS elsewhere in the script — reuse that, don't guess). If either sysfs path doesn't exist on a given host (e.g. a VM without full DMI emulation), don't error — log and continue, matching this project's existing graceful-degradation convention.

### 2. `crates/pharos-pulse/src/main.rs`: add `uuid` (Linux via the now-readable file; macOS/Windows via their existing mechanisms)

- Linux: mirror `get_serial_number()`'s exact shape, reading
  `/sys/class/dmi/id/product_uuid`.
- macOS: `IOPlatformUUID` is already present in the same `ioreg -rd1 -c
  IOPlatformExpertDevice` output `get_serial_number()` already parses for
  `IOPlatformSerialNumber` — extend the existing parsing to also capture
  this line rather than spawning a second `ioreg` process.
- Windows: `Win32_ComputerSystemProduct`'s `UUID` property via a second
  `Get-CimInstance` call (this is a different WMI class than `Win32_Bios`,
  which doesn't carry UUID).

### 3. `crates/pharos-pulse/src/main.rs`: add `manufacturer`/`product_name` (no permission fix needed)

- Linux: `/sys/class/dmi/id/sys_vendor` (→ `manufacturer`) and
  `/sys/class/dmi/id/product_name` — both typically world-readable, no ACL
  grant required. Confirm this empirically rather than assuming; if either
  turns out to also be restricted on some distro, fold it into item 1's
  tmpfiles.d grant rather than treating it as a surprise.
- macOS/Windows: use whatever equivalent mechanism is simplest
  (`system_profiler SPHardwareDataType` or extend the existing `ioreg`
  parse for macOS; `Win32_ComputerSystem`'s `Manufacturer`/`Model` for
  Windows) — don't over-engineer parity with Linux's exact field names if
  the platform's natural source differs; keep the Pharos field names
  (`manufacturer`, `product_name`) consistent across all three platforms
  regardless of source command.
- Same graceful `"unknown"`-on-failure and `inv.retain` filtering pattern
  as every other inventory field — no special-casing.

## Non-goals (do not touch)

- Do not use `dmidecode` anywhere — it needs broader privileges than a
  scoped file-read ACL and can do more than this use case needs.
- Do not grant `pharos` broad root/sudo access, or a systemd capability
  wider than what's needed for exactly these two files.
- Do not touch `pharos-scan` or `mdb`/`ph` — this is purely a
  `pharos-pulse` inventory-collection fix plus its installer support.
- Do not add any new field validation on the server side for these fields
  (unlike `ip_addr`/`mac_addr`, these are opaque hardware identifiers with
  no meaningful format to validate against).

## Verification steps (concrete, live)

1. **Podman-testable part**: confirm `manufacturer`/`product_name`
   collection works end-to-end against a real disposable node + server
   (these aren't permission-gated, so this part *is* faithfully
   Podman-testable) — real `mdb` query showing both fields with correct
   values matching what's actually in that container's `/sys/class/dmi/id/`
   (or its equivalent fallback, if a container doesn't expose it at all —
   report which case actually occurs).
2. **Not Podman-testable — requires a real host**: install/upgrade
   `pharos-pulse` on an actual bare-metal or VM Linux host (the reporting
   user has direct access to real hosts, e.g. `rdelgadoXPS15`) and confirm,
   before vs. after: `serial_number` and `uuid` are completely absent
   before the fix, present with correct real values after, without a
   reboot being required (the immediate `systemd-tmpfiles --create` step
   from item 1 must make this work without waiting for next boot).
   Separately confirm the grant survives an actual reboot (harder to
   verify without one, but at minimum re-run `systemd-tmpfiles
   --create` a second time and confirm it's idempotent/doesn't error).
3. Confirm the ACL grant is exactly as narrow as intended — `getfacl
   /sys/class/dmi/id/product_serial /sys/class/dmi/id/product_uuid` on the
   real host shows only the expected `pharos` read grant added, nothing
   broader.
4. `cargo test --workspace` passes (unit tests for the new field-parsing
   logic, mocked/stubbed the same way `get_serial_number()`'s existing
   tests presumably already are — check the existing test pattern and
   match it, don't invent a new one).
5. Confirm `mdb'*' return hostname serial_number uuid manufacturer
   product_name` against the real fleet (once deployed) actually now shows
   values, not just a passing test.
