# Plan: skip the IP-drift warning for certs with no IP SANs at all

## Background

`check_cert_ip_drift()` (`scripts/install.sh:123-153`, quoted verbatim, re-read fresh this
session):

```bash
check_cert_ip_drift() {
    local cert_path=$1
    local cert_label=$2
    local current_ips san_ips missing_ips=""

    current_ips="$(hostname -I 2>/dev/null || true)"
    if [[ -z "${current_ips}" ]]; then
        return
    fi

    san_ips="$(${SUDO} openssl x509 -in "${cert_path}" -noout -ext subjectAltName 2>/dev/null \
        | grep -o 'IP Address:[0-9.]*' | cut -d: -f2 || true)"

    local ip
    for ip in ${current_ips}; do
        if [[ "${ip}" == "127.0.0.1" ]]; then
            continue
        fi
        ...
        if ! grep -qx "${ip}" <<< "${san_ips}"; then
            missing_ips="${missing_ips} ${ip}"
        fi
    done

    if [[ -n "${missing_ips}" ]]; then
        warn "Certificate '${cert_label}' (${cert_path}) does not cover this host's current LAN IP(s):${missing_ips}"
        ...
        warn "To fix: remove ${cert_path} and its .key, then re-run this installer to regenerate the certificate with the current IP(s)."
    fi
}
```

**The false positive**: real evidence from the Implementation team's hub (a real Let's Encrypt
cert, by design containing only hostname SANs, no IP SANs at all — public CAs never issue
IP-SAN certs for private/dynamic addresses). Every `install.sh -- hub` re-run — which they will do
for every future version upgrade — triggers this warning, telling them to regenerate a cert that
is working exactly as intended. Following the suggested "fix" would destroy their real certificate
in favor of a self-signed one.

**Why this is safe to detect structurally, not just for this one case**: `setup_pki()`'s own
cert-generation logic (`scripts/install.sh:220-225`, unmodified) **unconditionally** includes
`IP.1 = 127.0.0.1` in every certificate it generates, with zero exceptions:

```bash
        echo "DNS.${dns_index} = localhost"
        echo "IP.1 = 127.0.0.1"
        local ip_index=2
        for ip in ${lan_ips}; do
            echo "IP.${ip_index} = ${ip}"
            ip_index=$((ip_index + 1))
        done
```

This means: a certificate with **zero** IP SANs at all could never have been generated by this
script's own `setup_pki()` — it's a reliable structural signal that the cert is externally
managed (a real CA, manually provisioned, or otherwise outside `install.sh`'s own cert-generation
path), not a Pharos self-signed cert that has since drifted. The IP-drift question is only
meaningful for the latter case.

## The change

Add an early return right after computing `san_ips`, before the per-IP comparison loop:

```bash
    san_ips="$(${SUDO} openssl x509 -in "${cert_path}" -noout -ext subjectAltName 2>/dev/null \
        | grep -o 'IP Address:[0-9.]*' | cut -d: -f2 || true)"

    # A cert with zero IP SANs at all was never generated by this script's own setup_pki(), which
    # always includes at least 127.0.0.1 - this is almost certainly an externally-managed cert
    # (e.g. a real public CA like Let's Encrypt, which never issues IP-SAN certs for private/
    # dynamic addresses). The "does this cover your current LAN IP" question doesn't apply to that
    # case and would otherwise be a permanent false positive on every future install.sh run.
    if [[ -z "${san_ips}" ]]; then
        return
    fi

    local ip
    for ip in ${current_ips}; do
        ...
```

## Non-goals (do not touch)

- **Do not** attempt to detect the cert's issuer/CA specifically (e.g. parsing whether it's
  actually Let's Encrypt) — the "zero IP SANs" structural signal is sufficient and doesn't require
  guessing at issuer identity.
- **Do not** change the existing IPv6-skip behavior or the `127.0.0.1`-skip behavior in the loop —
  unrelated, already correct, already documented.
- **Do not** change what happens when a cert *does* have at least one IP SAN but is still missing
  the host's current IP (the genuine drift case this function exists to catch) — that behavior is
  correct and unchanged.
- **Do not** touch `setup_pki()` itself — only reading its established, unconditional-127.0.0.1
  behavior as the basis for this fix, not modifying it.

## Verification steps (concrete)

1. **Regression case**: extract `check_cert_ip_drift` (per this repo's established testing
   convention — never `source scripts/install.sh` directly) and run it against a real self-signed
   cert generated by the actual `setup_pki()` function, with a fake `hostname -I` override
   simulating a changed LAN IP. Confirm the warning **still fires** exactly as before — this is
   the genuine drift case and must not be silently suppressed by this fix.
2. **The actual fix**: generate a real cert with `openssl` that has **zero** IP SANs at all
   (matching the shape of a real Let's Encrypt cert — hostname-only SAN), run
   `check_cert_ip_drift` against it with a `hostname -I` override reporting some LAN IP not in the
   cert, and confirm **no warning fires** — proving the false positive is actually fixed.
3. **Edge case**: confirm a cert with `127.0.0.1` as its *only* IP SAN (no other LAN IPs) still
   triggers the warning correctly if the host's real LAN IP is missing — this is a genuine
   Pharos-generated cert missing LAN-IP coverage (not the "zero SANs at all" case this fix targets)
   and must still be caught.
4. Clean up all test certs/containers.
